# Статус реализации MVP относительно ТЗ

Дата сверки: по состоянию репозитория после первой реализации. Ниже — что сделано, что проверено и где реализация **отличается** от ТЗ либо ещё не сделана.

## Проверено (на чистой сборке `docker compose build && up`)

| Что | Результат |
|---|---|
| Backend: unit + интеграционные тесты на PostgreSQL | 105 тестов, все проходят |
| Frontend: Vitest | 5 тестов, проходят |
| E2E Playwright (desktop + mobile) | 10 сценариев проходят: полный цикл заявки, возврат на доработку, изоляция клиентов, дашборд = seed, создание пользователя и смена пароля, QR-ссылка и мобильный кабинет, потеря сети, axe (0 serious/critical), reduced-motion, отсутствие внешних запросов |
| Demo-данные | Счётчики совпадают с ТЗ 12.5.6 (116 событий, 16 назначений, 13 отчётов, 8 актов…); метрики дашборда и непрочитанные уведомления совпадают с 12.6/12.7 |
| Сохранность данных | `docker compose down` + `up`: данные на месте; `backup.sh` → полная очистка томов → `restore.sh`: заявки и файлы восстановлены, `verify-storage` чист |

## Отличия от ТЗ

| ТЗ | Реализация | Причина |
|---|---|---|
| PDF через WeasyPrint | ReportLab + DejaVu Sans | без системных библиотек Pango, проще образ (запасной вариант из ТЗ) |
| Роли БД `app_rw`/`app_migrator` | одна роль приложения; неизменяемость журналов обеспечивают триггеры | упрощение MVP |
| Seed в `backend/seed/demo/*.json` | данные в Python (`backend/seed/loader.py`), создаются через те же функции workflow, что и в приложении | гарантирует согласованность событий, SLA и уведомлений |
| `reset-demo` удаляет только demo-строки | очищает **все** таблицы (`TRUNCATE`), только в dev/test/demo | события неизменяемы триггером |
| CSRF-токен в таблице sessions | токен вычисляется как HMAC от cookie сессии | меньше состояния |
| Раздел 10: пересчёт метрик в SQL | метрики считаются в Python по выборке видимых заявок | достаточно для MVP, верифицировано тестами; для >10⁵ заявок нужна оптимизация |
| Идемпотентность `PUT /report`, `PATCH` | только у POST-операций из ТЗ 5.9; остальное защищено `version` | по ТЗ |
| Встроенный сканер QR | через `BarcodeDetector` (где поддерживается) + ручной поиск; основной путь — штатная камера | отдельная библиотека не добавлялась |
| `GET /tickets/export.csv`, `GET /analytics/tickets-by-status`, `/analytics/sla`, `/analytics/repeat-failures` | нет отдельных эндпоинтов: всё в `/analytics/summary` и `/analytics/metric-tickets` | SHOULD-пункты |
| Номер версии Node в образе | `node:24-alpine` (текущий LTS на момент сборки, проверено установкой) | |


## Рабочее пространство заявок (канбан) — второй этап

Реализовано в `frontend/src/board/*`, `frontend/src/pages/Workspace.tsx`, `backend/app/realtime.py`, `backend/app/routers/events.py`.

| Требование | Реализация |
|---|---|
| Представления: Канбан (по умолчанию), Список, Календарь, Диаграмма Ганта / шкала SLA | Все четыре; календарь и шкала считают «сейчас» по часам сервера (`X-Server-Time`) |
| Фильтры: статусы, приоритеты, инженеры, диапазон дат, поиск с автодополнением | Мультивыбор, поиск по номеру, названию, оборудованию, клиенту, инженеру; фильтрация на клиенте по загруженным заявкам |
| 5 колонок со счётчиком, предупреждениями SLA и кнопкой «+» | Да. «+» активна в «Новая» (клиент, диспетчер) и «Принята / Назначена» (диспетчер: создаёт и сразу назначает). В остальных колонках заявку создать нельзя по правилам процесса — кнопка неактивна с пояснением |
| Перетаскивание | `@dnd-kit/core`, подсветка допустимых колонок. Правила — `resolveDrop` + `allowed_actions` сервера: «начать»/«продолжить» выполняются сразу (оптимистично, с откатом), остальные открывают диалог с обязательными полями; недопустимое — сообщение, карточка остаётся |
| Карточка | Номер-ссылка, приоритет, тема, оборудование и модель, клиент, площадка, SLA (обратный отсчёт / просрочка с пульсирующей границей), инженер с аватаром, прогресс чек-листа, запчасти, комментарии |
| Панель справа ≈60% | Выдвижная, состояние в URL (`?t=`), вкладки: Обзор (паспорт, история клиента, SLA, действия), Чек-листы (пошаговое заполнение с автосохранением), Запчасти и материалы, Журнал и чат (комментарии, фото, история с изменениями SLA) |
| Реальное время | **SSE** (не WebSocket): PostgreSQL `LISTEN/NOTIFY` внутри транзакции действия (доставка только после COMMIT) → `/api/v1/events/stream`; клиент перечитывает данные по REST, поэтому права проверяются как обычно; внутренние события клиентам не рассылаются; карточки, изменённые другими, подсвечиваются |
| LocalStorage | Представление, плотность и фильтры сохраняются отдельно для каждого пользователя |
| Плотность | Стандартная и компактная |
| Палитра и шрифт | Синий сайдбар `#0F172A`, фон `#F4F5F7`, акцент `#0D7A5F`, красный `#DE350B`, оранжевый `#F59E0B`; шрифт Inter (самохостинг через `@fontsource-variable/inter`, без внешних CDN) |

Отличия и ограничения:
- **Tailwind CSS не используется** — прежний CSS на токенах (проект уже на нём построен); React сохранён.
- **Списание запчастей со склада не реализовано**: складской учёт вне MVP. Вкладка фиксирует использованные позиции (коды `SP-…`), что попадает в акт.
- Фильтры работают по загруженному набору (до 1000 заявок); при большем объёме нужна серверная фильтрация.
- Колонка «Закрыта» включает также отклонённые и отменённые заявки.
- Тесты: backend 108, Vitest 15, E2E 15 (включая перетаскивание, живое обновление между двумя браузерами, фильтры после перезагрузки, axe). Один раз наблюдался нестабильный прогон E2E-02 после пересборки; три повторных прогона и два полных — зелёные, причина не установлена.

# Раздел 14. Этапы разработки, процесс и итоговые списки

## 14.1. Команда и допущения по срокам

Команда из трёх человек (ДП распределения; роли можно совмещать):

| Условное имя | Основная зона | Вторичная зона |
|---|---|---|
| **A — Backend/архитектор** | FastAPI, БД, бизнес-правила, безопасность | ревью миграций и прав |
| **B — Frontend/UX** | React, дизайн-система, мобильный кабинет | E2E-тесты UI |
| **C — Fullstack/DevOps/QA** | Docker, CI, worker, PDF, backup, тест-инфраструктура | seed, нагрузочные тесты |

Оценки — **ориентировочные** для студенческой команды при ~20–25 рабочих часах в неделю на человека, без учёта сессий и каникул. Сумма последовательных длительностей — 18.5 недели; за счёт параллельной работы frontend и backend календарно ожидается **16–20 недель**. Перед стартом оценки уточняются на этапе 1.

| № | Этап | Длительность, нед. | Основной результат |
|---|---|---|---|
| 1 | Уточнение требований | 1.0 | ТЗ v1.0, решения по ДП, макеты, бэклог |
| 2 | Репозиторий, архитектура, Docker | 1.5 | Пустой каркас запускается в Compose, CI зелёный |
| 3 | База, миграции, авторизация | 2.0 | Вход, пользователи, организации, площадки, аудит |
| 4 | Оборудование и QR | 1.5 | Реестр, паспорт, QR, этикетки |
| 5 | Заявки и назначения | 2.5 | Жизненный цикл заявки, SLA-часы, таймлайн |
| 6 | Кабинет инженера | 2.0 | Мобильные задания, чек-лист, запчасти, пауза |
| 7 | Файлы, акты, подтверждение | 2.5 | Фото/документы, PDF-акты, подтверждение/возврат |
| 8 | Уведомления и аналитика | 1.5 | Уведомления, worker, плановые заявки, дашборд, demo |

## 14.4. Правила Git и pull request

| Тема | Правило |
|---|---|
| Модель ветвления | GitHub-flow: `main` всегда пригоден к развёртыванию; короткие ветки `feat/<id>-кратко`, `fix/<id>-…`, `chore/…`, `docs/…`; прямые коммиты в `main` запрещены |
| Коммиты | Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, `ci:`, `build:`, `perf:`), сообщение на русском или английском (единый выбор команды) |
| Слияние | Squash-merge после успешного CI и ревью; ветка удаляется |
| Защита `main` | Обязательные проверки CI; ≥ 1 одобрение; для миграций, прав доступа, `TicketWorkflow`, SLA, Docker/Compose, безопасности — ≥ 2 (через `CODEOWNERS`) |
| Размер PR | Цель ≤ 400 строк изменений; крупные задачи делятся на стадии за feature-флагами или цепочкой PR |
| Версии | SemVer-теги `vMAJOR.MINOR.PATCH` на `main`; `CHANGELOG.md` по Keep a Changelog; образы тегируются `APP_VERSION` |
| Секреты | Запрещены в коде и истории; при утечке — немедленная ротация и очистка истории |
| Миграции | Не редактировать выпущенные миграции; новая миграция — отдельный PR-коммит с проверкой `downgrade` на пустой БД |

**Шаблон PR (чек-лист):** описание и ссылка на задачу · затронутые разделы ТЗ · скриншоты/GIF для UI · миграции (да/нет, обратимость) · права и изоляция данных (что проверено) · тесты (какие добавлены) · документация/OpenAPI обновлены · влияние на Docker/окружение · риски и откат.

## 14.6. Definition of Done

Задача считается завершённой, когда выполнены **все** пункты:

1. Реализовано поведение из ТЗ и критерии приёмки соответствующего раздела; отступления зафиксированы в ADR/ДП.
2. Есть автотесты нужного уровня (unit/integration/E2E); для правил доступа — позитивные **и негативные** кейсы.
3. CI зелёный; покрытие не ниже порогов R-3/R-4 для затронутых модулей.
4. Проверка прав на backend: новые эндпоинты занесены в матрицу IT-01 и используют `VisibilityPolicy`.
5. Миграции обратимы (`downgrade`) и совместимы по правилу expand/contract; `alembic check` без расхождений.
6. OpenAPI актуален; контрактные тесты IT-35 проходят; типы frontend перегенерированы.
7. UI: состояния загрузки/пусто/ошибка, подтверждения действий, доступность (клавиатура, фокус, контраст), мобильный вид проверены; нет захардкоженных строк вне `i18n`.
8. Нет секретов и персональных данных в коде, логах и тестовых данных.
9. Документация обновлена (README, `docs/`, runbook при необходимости); `.env.example` дополнен новыми переменными.
10. Код прошёл ревью, замечания закрыты, PR влит squash-мерджем.
11. Для затрагивающих Docker/эксплуатацию задач — проверен запуск «с нуля» (OP-01) и перезапуск (OP-02).

## 14.7. Риски проекта

| Риск | Вероятность / влияние | Снижение |
|---|---|---|
| Требования компании изменятся после старта (SLA, формат акта, чек-листы) | Средняя / высокая | Параметры SLA в БД; шаблоны чек-листов и акта версионируются; ДП собраны в одном списке |
| Объём работ превышает возможности команды | Высокая / высокая | Строгое разделение MUST/SHOULD; SHOULD отсекаются первыми; еженедельный контроль фактической скорости |

# Раздел 6. Функциональные требования

Для каждого модуля указаны: назначение, действия по ролям, поля и валидация, основной сценарий, ошибки и исключения, критерии приёмки. Общие правила валидации действуют на backend (Pydantic) и дублируются на frontend (zod); при расхождении источник истины — backend.

**Общие правила:**

* Строки обрезаются по краям (`strip`), пустая строка приравнивается к отсутствующему значению для необязательных полей.
* Текст допускает любые Unicode-символы; HTML не интерпретируется (экранирование при выводе; в PDF — через автоэкранирование Jinja2).
* Ошибки валидации: `422 VALIDATION_ERROR` с массивом `details.fields[]` (`field`, `code`, `message`).
* Изменяемые сущности имеют `version`; `PATCH` без актуальной `version` → `409 VERSION_CONFLICT`.
* Архивирование обратимо; физического удаления бизнес-данных нет.

## 6.1. Авторизация и пользователи

**Назначение.** Аутентификация, управление учётными записями, отзыв доступа.

| Действие | admin | dispatcher | engineer | manager | client |
|---|---|---|---|---|---|
| Войти / выйти / сменить свой пароль | ✓ | ✓ | ✓ | ✓ | ✓ |
| Просмотр списка пользователей | ✓ все | ✓ инженеры и клиенты (ФИО, роль, организация, загрузка) | — | ✓ | — |
| Создать, изменить, деактивировать, сбросить пароль, отозвать сессии | ✓ | — | — | — | — |
| Свои сессии: список, отзыв | ✓ | ✓ | ✓ | ✓ | ✓ |

**Поля и валидация (пользователь).**

| Поле | Правило |
|---|---|
| `email` | Обязательно, формат e-mail, ≤ 254, уникален без учёта регистра, хранится в нижнем регистре |
| `full_name` | 2–120 символов |
| `phone` | Необязательно; `^\+?[0-9 ()\-]{7,20}$` |
| `role` | `admin`/`dispatcher`/`engineer`/`manager`/`client` |
| `organization_id` | Обязательно; роль `client` ⇔ организация `kind=client` |
| `capacity` (только `engineer`) | Целое 1–20, по умолчанию 4 — максимум одновременных активных заявок (для расчёта загрузки) |
| `password` (смена) | ≥ 12 символов, ≤ 128, не равен email и ФИО, не в списке частых паролей |

**Основной сценарий.** Администратор создаёт пользователя → получает временный пароль (показан один раз, кнопка «Копировать») → передаёт пользователю вне системы → пользователь входит, система требует сменить пароль → пользователь работает по своей роли.

**Ошибки и исключения.**

| Ситуация | Ответ |
|---|---|
| Неверный email/пароль (сообщение одинаково для обоих случаев) | `401 INVALID_CREDENTIALS` |
| Превышено число попыток | `423 ACCOUNT_LOCKED` (`details.locked_until`) |
| Деактивированный пользователь входит | `401 INVALID_CREDENTIALS` (без раскрытия причины) |
| Временный пароль просрочен | `401 INVALID_CREDENTIALS`; администратор делает сброс |
| Не сменён временный пароль | `403 PASSWORD_CHANGE_REQUIRED` |
| Дубликат email | `409 DUPLICATE` |
| Деактивация последнего администратора / себя / инженера с активными назначениями | `409 LAST_ADMIN_PROTECTED` / `409 SELF_DEACTIVATION` / `409 USER_HAS_ACTIVE_ASSIGNMENTS` |

**Критерии приёмки.** Вход и выход работают; сессия отзывается при деактивации (следующий запрос → `401`); временный пароль виден один раз; смена пароля отзывает остальные сессии; регистрации нет; все действия администратора пишутся в `audit_log`.

**Назначение.** Справочники владельцев оборудования и мест размещения; основа изоляции данных клиентов.

| Действие | admin | dispatcher | engineer | manager | client |
|---|---|---|---|---|---|
| Просмотр | ✓ | ✓ | в контексте своих заявок | ✓ | ✓ своя организация |
| Создание / изменение | ✓ | — | — | — | — |
| Архивирование | ✓ | — | — | — | — |

**Поля.**

| Сущность | Поле | Правило |
|---|---|---|
| Организация | `kind` | `service` (ровно одна) или `client`; не меняется после создания |
| | `name` | 2–200, уникально без учёта регистра |
| | `short_name` | ≤ 60 |
| | `bin_iin` | Необязательно, 12 цифр (формат без проверки контрольной суммы — ДП), уникально среди непустых |
| | `contact_email`, `contact_phone`, `address` | формат e-mail / телефон / ≤ 300 |
| Площадка | `organization_id` | Клиентская организация |
| | `name` | 2–120, уникально в пределах организации |
| | `address` | 5–300 |
| | `timezone` | Название IANA (`Asia/Almaty` по умолчанию) |

**Сценарий.** Админ создаёт клиентскую организацию → площадки → пользователей `client` → оборудование.

**Ошибки.** Архивирование организации с активными заявками → `409 HAS_ACTIVE_TICKETS`; площадки с неархивным оборудованием → `409 HAS_ACTIVE_EQUIPMENT`. Пользователи архивной клиентской организации не могут войти (`401`), история сохраняется.

**Приёмка.** Клиент получает только свою организацию и её площадки; архивирование не удаляет заявки и акты; составной внешний ключ не позволяет привязать оборудование к площадке чужой организации (тест на уровне БД).

## 6.3. Оборудование и цифровой паспорт

**Назначение.** Реестр единиц оборудования и карточка-паспорт с историей.

| Действие | admin | dispatcher | engineer | manager | client |
|---|---|---|---|---|---|
| Реестр и поиск | ✓ | ✓ | только оборудование с видимой заявкой | ✓ | ✓ своё |
| Создание / изменение | ✓ | ✓ | — | — | — |
| Архивирование | ✓ | — | — | — | — |
| Загрузка документов к паспорту | ✓ | ✓ | — | — | — |

**Поля и валидация.**

| Поле | Правило |
|---|---|
| `organization_id`, `site_id` | Обязательно; площадка принадлежит организации |
| `type` | `transformer` / `substation` / `switchgear` |
| `inventory_number` | 1–50, уникален в организации |
| `name` | 2–150 |
| `manufacturer`, `model`, `serial_number` | ≤ 100; серийный номер уникален в паре (`manufacturer`, `serial_number`), если оба заданы |
| `manufacture_year` | 1950…текущий год+1 |
| `commissioned_on` | Дата ≤ сегодня и ≥ 1 января года выпуска |
| `voltage_class_kv` | > 0 и ≤ 1150 |
| `rated_power_kva` | Обязательно для `transformer`, `substation`; > 0 |
| `technical_state` | `operational` / `degraded` / `out_of_service`; меняется диспетчером/админом вручную в MVP |
| `passport_data` | JSON по схеме типа (см. ниже) |
| `location_description` | ≤ 300 («Ячейка 3, подстанция ТП-12») |

Схемы `passport_data` (все поля необязательны, тип проверяется): *transformer* — `cooling_type` (`ONAN`/`ONAF`/`dry`/`other`), `oil_mass_kg`, `vector_group`, `primary_kv`, `secondary_kv`; *substation* — `scheme`, `transformers_count`, `cabinets_count`; *switchgear* — `cells_count`, `breaker_type`, `insulation` (`air`/`gas`/`other`).

**Паспорт (экран) включает:** основные поля; состояние; QR; документы; плановые даты (ближайшая и последняя); активные заявки; история заявок (таймлайн: номер, дата, вид, статус, диагноз, выполненные работы, запчасти, ссылка на актуальный акт — по правам); счётчик повторных неисправностей за 90 дней.

**Сценарий.** Диспетчер создаёт оборудование → QR генерируется автоматически → печатает этикетку → клиент видит оборудование в реестре.

**Ошибки.** Дубликат инвентарного номера → `409 DUPLICATE`; площадка чужой организации → `422`; изменение архивного оборудования → `409 EQUIPMENT_ARCHIVED`.

**Приёмка.** Поиск по инвентарному и серийному номеру, названию (регистронезависимо, подстрока); клиент не находит оборудование других организаций по прямому номеру/QR; история сохраняется после архивирования.

## 6.4. QR-коды

**Назначение.** Быстрое открытие паспорта оборудования с телефона.

| Параметр | Требование |
|---|---|
| Содержимое QR | Только URL: `{APP_PUBLIC_URL}/e/{qr_code}`. Персональные и служебные данные в QR не кодируются |
| `qr_code` | 12 символов из алфавита `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (без похожих 0/O, 1/I/L), генерируется криптослучайно, уникален |
| Безопасность | QR **не является секретом и не даёт доступа**: после перехода требуется вход, затем проверяется область видимости |
| Форматы | SVG и PNG (коррекция ошибок уровня M, поле ≥ 4 модулей); этикетка PDF (A4, 2×4 этикетки: QR, название, инвентарный номер, площадка) |
| Перевыпуск | `admin`/`dispatcher`; старый код немедленно перестаёт работать (`404`); событие в `audit_log` |

**Основной сценарий (инженер).** Сканирует QR штатной камерой телефона → открывается `https://…/e/{code}` → если нет сессии: страница входа и возврат на `/e/{code}` → SPA вызывает `GET /equipment/by-qr/{code}` → переход в паспорт; если у инженера есть активная заявка по этому оборудованию, вверху показывается баннер «Ваша заявка SR-… — открыть». Альтернатива — встроенный сканер на странице `/scan` (камера) или **ручной поиск** по инвентарному номеру, серийному номеру или номеру заявки.

**Исключения.**

| Ситуация | Поведение |
|---|---|
| Неизвестный/перевыпущенный код, либо оборудование вне области видимости | `404`, экран «Оборудование не найдено или недоступно» + поле ручного поиска (без указания, существует ли код) |
| Отказ в доступе к камере / нет камеры | Сообщение с инструкцией + ручной ввод кода/номера |
| Страница открыта по HTTP (не localhost) | Встроенный сканер недоступен (ограничение браузеров `getUserMedia` — только HTTPS); штатная камера телефона работает всегда, если URL доступен |

**Приёмка.** QR, напечатанный из системы, при сканировании в demo открывает правильный паспорт (E2E-03, ручная проверка на 2 устройствах — OP-07); чужой код у клиента/инженера → `404`; после перевыпуска старый код → `404`.

| Поле | Правило |
|---|---|

**Сценарий.** Клиент выбирает оборудование (или приходит из паспорта/QR) → описывает проблему, срочность, прикладывает фото → отправляет → получает номер → следит по таймлайну.

**Ошибки.** Оборудование чужой организации → `404`; архивное → `409 EQUIPMENT_ARCHIVED`; повтор отправки → тот же ответ (идемпотентность); изменение заявки не в `new` клиентом → `409 TICKET_LOCKED`.

**Приёмка.** Создание за ≤ 3 действия из паспорта; номер уникален и непрерывен в рамках года (без пропусков при откате транзакции не гарантируется — ДП: допустимы пропуски); при создании диспетчеры получают уведомление; предупреждение о дубле показывается, но не блокирует.

## 6.6. Назначение инженеров

**Назначение.** Выбор исполнителя и контроль нагрузки.

| Действие | dispatcher | admin | manager | engineer | client |
|---|---|---|---|---|---|
| Назначить / переназначить | ✓ | — | — | — | — |
| Просмотр списка инженеров с загрузкой | ✓ | ✓ | ✓ | — | — |
| Просмотр истории назначений заявки | ✓ | ✓ | ✓ | своей | имя текущего инженера |

**Поля.** `engineer_id` (активный пользователь роли `engineer`), `scheduled_at` (необязательная плановая дата/время визита, ≥ now − 5 минут), `comment` ≤ 500, `reason` при переназначении ≥ 5, `version`.

**Правила.** Нагрузка инженера = число его заявок в статусах `assigned`, `in_progress`, `paused`; `load_pct = load / capacity`. При назначении на инженера с загрузкой ≥ 100% возвращается предупреждение `ENGINEER_OVERLOADED` (UI просит подтвердить), но запрета нет (ДП). Один исполнитель на заявку одновременно (БД-ограничение).

**Ошибки.** Неактивный инженер/не инженер → `422 ASSIGNEE_NOT_AVAILABLE`; тот же инженер → `422 SAME_ASSIGNEE`; конфликт версий → `409`.

**Приёмка.** Два параллельных назначения дают один успех и один `409`; история переназначений видна в таймлайне; инженер сразу после переназначения теряет доступ к заявке (`404`).

## 6.7. Диагностика и выполнение работ

**Назначение.** Рабочий отчёт инженера: диагностика, чек-лист, результаты, фото, запчасти.

| Действие | engineer (исполнитель) | dispatcher | manager | admin | client |
|---|---|---|---|---|---|
| Начать работу, пауза, продолжить, завершить | ✓ | пауза/продолжить | — | — | — |
| Редактировать черновик отчёта | ✓ | — | — | — | — |
| Просмотр отчёта | ✓ | ✓ | ✓ | ✓ | в составе акта |
| Запрос исключения по фото | ✓ | — | — | — | — |
| Решение по исключению по фото | — | ✓ | — | — | — |

**Поля отчёта.**

| Поле | Правило |
|---|---|
| `diagnosis` | До 4000, к завершению ≥ 20 |
| `work_performed` | До 4000, к завершению ≥ 20 |
| `result_code` | `resolved` / `resolved_with_remarks` |
| `result_summary` | До 1000, к завершению ≥ 10 |
| `recommendations` | До 2000; ≥ 10 при `resolved_with_remarks` |
| `labor_minutes` | Целое 0–10000 (информационное поле) |
| `checklist_answers` | Объект `{key: value}` по шаблону |
| `parts_confirmed` | boolean |
| `photo_exception_*` | См. 5.5 |
| `version` | Optimistic locking автосохранения |

**Шаблон чек-листа** (`checklist_templates.schema`, JSON). Версия шаблона **иммутабельна** после публикации; изменение = новая версия; заявка привязывается к версии, активной на момент первого запуска работ, и не «переезжает» при публикации новой.

| Поле пункта | Значение |
|---|---|
| `key` | `snake_case`, уникален в шаблоне |
| `section` | Группа пунктов (для отображения) |
| `label` | Текст ≤ 200 |
| `type` | `boolean` / `number` / `enum` / `text` |
| `required` | boolean |
| `unit`, `min`, `max` | Для `number` |
| `options` | Для `enum`: массив `{value, label, flag?}` |
| `flag_if` | Условие «не норма»: `{"equals": false}`, `{"gt": 80}`, `{"in": ["low"]}`; при срабатывании обязателен `answers[key].comment` |

Формат ответа: `"oil_temp_c": {"value": 62.5, "comment": null}`.

**Автосохранение.** UI сохраняет черновик через 1.5 с после изменения (`PUT /tickets/{id}/report`, с `version` отчёта). Конфликт версий отчёта (редактирование с двух устройств) → `409 VERSION_CONFLICT` и показ различий.

**Сценарий инженера.** Список заданий → открыл заявку/паспорт по QR → «Начать работу» → диагностика (текст + чек-лист) → фото «до» → ремонт → запчасти → фото «после» → «Завершить» → проверка полноты → акт сформирован → заявка в `awaiting_confirmation`.

**Пауза.** Пункт 5.3 (T7/T8). Все данные черновика сохраняются.

**Ошибки.** `422 COMPLETION_REQUIREMENTS_NOT_MET`, `409 REPORT_LOCKED` (правка отправленной ревизии), `422` при значениях вне диапазона.

**Приёмка.** Завершение невозможно без C1–C5; ответы чек-листа сохраняются с версией шаблона; два устройства не затирают друг друга без предупреждения; публикация новой версии не меняет уже начатые заявки.

## 6.8. Запчасти

**Назначение.** Справочник и фиксация **использованного** при ремонте (не склад).

| Действие | admin | dispatcher | engineer | manager | client |
|---|---|---|---|---|---|
| Справочник: просмотр | ✓ | ✓ | ✓ | ✓ | — |
| Справочник: создание, изменение, деактивация | ✓ | ✓ создание/изменение | — | — | — |
| Добавить/изменить/удалить позицию использования (в черновике) | — | — | ✓ исполнитель | — | — |
| Просмотр использованного | ✓ | ✓ | ✓ | ✓ | в акте |

**Поля справочника.** `sku` (1–40, уникален), `name` (2–150), `unit` (`pcs`/`l`/`kg`/`m`/`set`), `category` (≤ 60), `description` (≤ 500), `is_active`.

**Поля использования.** `spare_part_id` (активная позиция), `quantity` (> 0, ≤ 100000, до 3 знаков; для `pcs` и `set` — целое), `serial_or_batch` (≤ 80), `comment` (≤ 300). Единица измерения копируется в запись (`unit_snapshot`). Одна строка на (отчёт, позиция).

**Правила.** Остатки, цены, закупки, резервирование не ведутся. Деактивированная позиция остаётся в старых отчётах. Если позиции нет в справочнике — инженер просит диспетчера добавить (свободного текста в MVP нет — ДП, чтобы не плодить дубли).

**Ошибки.** Неактивная позиция → `422`; изменение после отправки отчёта → `409 REPORT_LOCKED`.

**Приёмка.** Список использованного попадает в акт; ожидание запчастей не блокирует заявку; запись в отчёте остаётся неизменной после деактивации позиции в справочнике.

## 6.9. Вложения и фотографии

| Параметр | Требование |
|---|---|
| Типы фото | JPEG, PNG, WebP — определение по **содержимому** (magic bytes + успешное открытие Pillow), а не по расширению/`Content-Type`. HEIC в MVP не принимается (`415 UNSUPPORTED_FILE_TYPE` с подсказкой «Включите формат JPEG/Most Compatible в камере»; клиентский код пробует уменьшить и конвертировать через `<canvas>`) — ДП |
| Документы | PDF (проверка заголовка `%PDF-` и структуры) |
| Размер | Фото ≤ 10 МБ, документ ≤ 20 МБ, пиксели ≤ 40 Мп; Nginx `client_max_body_size 25m` |
| Количество | ≤ 40 вложений на заявку, ≤ 100 на оборудование |
| Стадия фото | `before` / `during` / `after` / `other` (обязательна для фото в заявке) |
| Обработка | Фото перекодируется (удаление EXIF, включая геометки), создаётся миниатюра 480 px; хранится SHA-256 |
| Имя файла | Оригинальное имя хранится как метаданные (очищается от путей и управляющих символов); на диске — случайный ключ |
| Доступ | Только `GET /attachments/{id}/download` с проверкой прав; `Content-Disposition`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` |
| Видимость | `public` (видит клиент) / `internal` (только сервисные роли); по умолчанию `public`; инженер может пометить `internal` |
| Удаление | Мягкое (`deleted_at`) автором, пока отчёт — черновик и заявка не в терминальном статусе; в закрытых заявках удаление запрещено |
| Целостность | Запись в БД и файл согласованы по алгоритму 7.9; осиротевшие файлы убирает worker |
| Прогресс | UI показывает прогресс загрузки, повтор после ошибки с тем же `Idempotency-Key` |

**Ошибки.** `413 FILE_TOO_LARGE`, `415 UNSUPPORTED_FILE_TYPE`, `422 FILE_CORRUPTED`, `409 ATTACHMENT_LIMIT_EXCEEDED`, `409 TICKET_LOCKED` (загрузка в терминальную заявку).

**Приёмка.** Файл `.jpg` с содержимым исполняемого файла отклоняется; чужой файл не скачивается ни по прямому id, ни через PDF; EXIF-геометки отсутствуют в сохранённом файле (тест IT-18).

## 6.10. PDF-акты

**Назначение.** Документ о выполненных работах, формируемый из отправленной ревизии отчёта.

| Действие | engineer | client | dispatcher | manager | admin |
|---|---|---|---|---|---|
| Формирование | автоматически при `complete` | — | — | — | — |
| Просмотр / скачивание PDF | исполнитель | своя организация | ✓ | ✓ | ✓ |
| Подтверждение / возврат | — | ✓ | — | — | — |

**Содержание акта (макет — шаблон `act_v1`).**

1. Заголовок: «Акт выполненных работ», номер акта `{номер заявки}-A{версия}`, дата формирования (часовой пояс площадки + указание UTC).
2. Организации (сервисная, клиентская), площадка.
3. Оборудование: название, тип, инвентарный и серийный номер, производитель/модель.
4. Заявка: номер, вид, приоритет, даты создания, начала работ, завершения.
5. Исполнитель (ФИО), контакты клиента.
6. Диагностика, выполненные работы, результат, рекомендации.
7. Таблица чек-листа (пункт, значение, «норма/не норма», комментарий) с указанием версии шаблона.
8. Использованные запчасти (наименование, артикул, количество, единица).
9. Фотографии: до 6 миниатюр (до/после) с подписями и номерами вложений.
10. Блок «Подтверждение клиента»: статус в системе (на момент формирования — «ожидает подтверждения»), оговорка «Подтверждение в информационной системе не является квалифицированной электронной подписью».
11. Служебная строка: версия акта, версия шаблона, SHA-256 снимка данных, ссылка на заявку.

**Правила версий.**

| Правило | Значение |
|---|---|
| Номер версии | 1, 2, 3 … для заявки, растёт при каждом `complete` |
| Неизменяемость | PDF и `data_snapshot` не меняются; хэш PDF сохраняется |
| Актуальность | Ровно один акт `is_current=true` на заявку; при возврате старый становится `is_current=false` |
| Решение клиента | Хранится в `acts.decision` (`confirmed`/`returned`), `decided_by`, `decided_at`, `decision_comment`, `rating` |
| Лист подтверждения (SHOULD) | `GET /acts/{id}/confirmation.pdf` — одностраничная справка (кто, когда, хэш акта), формируется по запросу из БД |

**Генерация.** Синхронно внутри `complete` (лимит 20 с). Сначала PDF формируется в памяти и записывается в финальный путь со случайным ключом (через временный файл и атомарный `rename`); затем выполняется транзакция БД (7.9). Ошибка на любом шаге → заявка остаётся в `in_progress`, отчёт — черновиком, пользователь видит `500 ACT_GENERATION_FAILED` с `request_id` и может повторить `complete` тем же `Idempotency-Key` (для сохранённой ошибки ключ освобождается — ДП).

**Ошибки.** `409 ACT_OUTDATED`, `404` на чужой акт, `410`/`500 FILE_MISSING`, если файл утрачен (алерт, восстановление из backup).

**Приёмка.** PDF открывается в стандартных просмотрщиках; кириллица и казахские буквы (ә, ғ, қ, ң, ө, ұ, ү, һ, і) отображаются; повторное завершение создаёт версию 2, версия 1 остаётся доступной с отметкой «неактуален»; чужой PDF → `404`.

## 6.12. Плановое обслуживание

**Назначение.** Регулярные работы по интервалу и контроль плановых дат.

| Действие | admin | dispatcher | engineer | manager | client |
|---|---|---|---|---|---|
| Создание/изменение/деактивация плана | ✓ | ✓ | — | — | — |
| Просмотр планов и дат | ✓ | ✓ | asg | ✓ | свои (только чтение) |

**Поля плана.** `equipment_id`, `title` (3–150), `description` (≤ 1000), `interval_days` (1–1825), `lead_days` (0–60; по умолчанию 7), `priority` (по умолчанию `low`), `checklist_template` (по умолчанию — активный шаблон типа), `next_due_date` (первая плановая дата, ≥ сегодня), `is_active`.

**Правила генерации (worker, ежедневно в 05:00 UTC — ДП).**

1. Для каждого активного плана, у которого `next_due_date − lead_days ≤ сегодня` и по которому нет заявки с `(plan_id, plan_due_date = next_due_date)`, создаётся плановая заявка (`kind=planned`, `source=scheduler`, `created_by=NULL`, приоритет плана, заголовок «Плановое ТО: …»).
2. Уникальный индекс `(plan_id, plan_due_date)` исключает дубли при повторном запуске, перезапуске контейнера или параллельных воркерах.
3. После подтверждения (`closed`) плановой заявки: `last_done_on = дата закрытия (по часовому поясу площадки)`, `next_due_date = last_done_on + interval_days`. Отклонённая/отменённая плановая заявка `next_due_date` **не** сдвигает; диспетчер получает уведомление «плановая работа не выполнена» (ДП).
4. Просроченная плановая дата (`next_due_date < сегодня`, заявка не закрыта) отображается в паспорте и на дашборде как «просрочено планово».

**Приёмка.** Двойной запуск задачи создаёт ровно одну заявку; после закрытия дата сдвигается на интервал; клиент видит плановые даты только своего оборудования.

**Приёмка.** После T4 инженер видит уведомление не позднее следующего опроса; уведомление содержит ссылку на заявку, доступную получателю; клиенты не получают internal-событий; ожидаемые счётчики непрочитанных для demo — в разделе 12 (IT-26).
